# Antigravity：启动进程没有继承系统代理

## 已验证与未验证
2026-10-29 的 Antigravity 2.28.0 模型进程未继承代理；带 HTTP/HTTPS 代理环境重启后，原生 Gemini 真实返回 OK。后来另一次新账号登录 IPv6 超时，重启后主进程/语言服务具备代理环境，但新账号最终登录成功没有记录。不要混为全部已修复。

## 执行
1. 确认当前 App 路径、版本及日志超时；对照当前系统代理是否启用且可达。只检查必要的代理变量，不打印含凭据的完整环境。
2. 保存工作、正常退出 Antigravity，确认主进程和旧语言服务已结束。应用仍运行时再次 open 不会可靠替换原环境。
3. 优先检查本机是否已有可用启动器；没有时参考以下启动方式。读取 `scutil --proxy` 的 HTTPEnable/HTTPProxy/HTTPPort，未启用时停止，随后通过 `open -a /Applications/Antigravity.app --env ...` 注入 HTTP_PROXY、HTTPS_PROXY 及小写变体，并让 localhost、127.0.0.1、::1 绕过代理。运行前核对路径存在、内容无异常和当前端口监听。
4. 按上述逻辑使用当前 App 和代理启动，不写全局 shell 配置。不盲用历史固定端口。IPv6 代理地址需要合法 URL 方括号格式。
5. 查看新进程是否正确继承并观察实际连接；已有登录态先直接测试，不强迫重新登录。确实需要登录时完成官方浏览器 OAuth，确认回到正确账号。
6. 实际发“只回复 OK”，再完整退出并用同一启动方式复测。若仅手工启动能用，说明依赖启动器，不声称普通 Dock 启动已经永久修好。若当前版本支持官方代理设置，查该版文档再选择持久配置。
7. 无效时正常退出后按原方式重开；没有更改全局代理时无需“恢复”其他程序设置。若错误是 location unsupported 或 Verify，转入资格/身份分流，不继续网络重启循环。

## 来源与局限
- 本流程来自作者 macOS 实测，历史版本为2.28.0；新版本需重新核对。
- [官方认证流程](https://antigravity.google/docs/install/)：个人账号经浏览器 OAuth 返回 App。文档随版本变动，旧版修复不得无条件套新架构。

## 启动示例
仅在保存工作并完整退出应用、确认已有代理正常运行后执行。将示例端口换成当前系统 HTTP 代理端口；不要把 SOCKS 端口误填为 HTTP。

```sh
open -a /Applications/Antigravity.app \
  --env 'HTTP_PROXY=http://127.0.0.1:YOUR_HTTP_PORT' \
  --env 'HTTPS_PROXY=http://127.0.0.1:YOUR_HTTP_PORT' \
  --env 'http_proxy=http://127.0.0.1:YOUR_HTTP_PORT' \
  --env 'https_proxy=http://127.0.0.1:YOUR_HTTP_PORT' \
  --env 'NO_PROXY=localhost,127.0.0.1,::1' \
  --env 'no_proxy=localhost,127.0.0.1,::1'
```

## 补充历史复核（2026-11-26）

### 分支 A：修好一次，普通图标重开又不能用
这是原代理继承故障的复发条件，不能计作另一种已修复根因。2026-10-29交付记录明确说明：启动器只给该次 Antigravity 进程注入代理，没有更改全局环境；普通图标启动不会持久继承。后续用户确实再次反馈无法用模型。

- 先确认本次如何启动，检查当前主进程和语言服务是否仍带有效代理；不能只因上次修过就默认已经继承。
- 如果当前代理已正确继承，停止重复注入，读取本次真实错误并用下方分支 B 复测。
- 如代理缺失，保存工作，完整退出旧主进程及语言服务，再使用已验证启动器。分别记录当前会话可用、同方式重开可用、普通图标重开可用；未测项明确留空。
- 不把用户的普通启动入口悄悄替换成常驻服务；用户要求持久化时，先查当前版本官方代理设置，再选最小可恢复方案。历史未验证任何永久启动补丁。

### 分支 B：旧请求报错，但当前新请求已经恢复
2026-10-29至30日原始会话中，旧请求曾返回 HTTP 400 `User location is not supported for the API use`。当时当前进程仍带代理，未改配置或切换线路，新会话的 Gemini 3.8 Flash Medium 先后真实返回 `OK`、`OK2`。这是“当前调用恢复可用”的实测，不能宣传为永久解决地区限制，也不能推断新会话本身改变了资格。

操作：
1. 对齐错误时间、账号、模型与当前请求，先区分旧失败气泡和新发生的故障。
2. 在原生 Antigravity 新建一个无敏感信息的测试会话，明确禁止读写文件和调用工具，发“连接诊断：只回复 OK”；成功后再发“第二次连接诊断：只回复 OK2”。
3. 两次返回正确且没有降级提示时，只报告所测账号/模型当前可用，保留用户旧对话，不删除历史，也不重复清库、改代理或改会员。恢复旧工作流时让用户原请求重新发起；旧错误气泡不会自动变成成功。
4. 若新请求仍报地区/Verify，按新的原始错误进入资格核对；若传输超时，才回到代理分支。不要拿旧400覆盖当前连接事实。

### 分支 C：Antigravity CLI 查模型超时（仅目录查询验证）
2026-11-26本机实测：`agy models` 默认启动超时；使用从当前系统核对到的 HTTP/HTTPS 代理环境后成功返回模型目录。沙箱内另有日志目录写入与本地端口绑定被拒绝，属于执行权限限制，不是 Google 登录失败。

- 此分支仅在用户请求CLI/集成时适用；Gemini App、Antigravity App、Antigravity CLI是不同入口，不互相替代。
- 先分类本地 permission denied/bind denied 和实际网络超时。按工具权限规则取得必要本机执行能力；不关闭安全校验或修改认证文件。
- 查询当前系统代理，仅给本次CLI进程注入 HTTP_PROXY/HTTPS_PROXY、小写变体及本机NO_PROXY。不要硬编码历史端口或声称修改了App的网络状态。
- `agy models` 返回只验收模型目录。登录修复或生成能力仍需在用户指定入口完成真实对话，本次未完成CLI生成测试，不能写成CLI全面修复。

### 未证实成功与明确排除
- 新账号IPv6超时：已验证代理接口可响应、主进程与语言服务继承代理；最终新账号登录没有证据。旧账号Verify页曾被误认，必须逐页核对目标账号。
- 地区资格：账号条款关联地区、Google Play国家、付款资料和家庭组是不同字段。历史地区不是当前地区；不凭付款地址或出口IP推断资格。现行要求按当前官方说明核对，不为尝试修复退出家庭组。
- 模型/额度能显示、更新到某版本，都不证明能生成。历史升级后仍有HTTP400，不能把升级单独列为成功解法。
- 第三方用量面板的Token计价修复属于面板项目，不属于Antigravity客户端修复，未纳入。

### 证据强度
代理继承成功来自当时交付记录与原生对话验证；新会话恢复来自原始工具回读中可见的OK和OK2；CLI分支来自实际命令退出结果。以上为历史成功范围，不是2026-11-26再次复现全部App故障，也不代表所有相似错误同因。
